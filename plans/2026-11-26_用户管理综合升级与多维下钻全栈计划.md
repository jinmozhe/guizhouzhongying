# 用户管理综合升级与多维下钻全栈计划

## 1. 当前状态和结果

- 当前状态：已结束
- 结束结果：已完成；后端用户列表按权批量聚合会员等级与双轨钱包并支持等级筛选、新增按用户查询双轨钱包流水与用户综合详情接口、OpenAPI 与客户端生成、管理端对称物业可点击标签与操作列“更多”菜单、头像/会员等级/佣金余额列、三套抽屉（WalletLedgerDrawer、MemberHistoryDrawer、UserDetailDrawer）及跨页带参跳转闭环均已完成，全栈轻量与仓库治理门禁全部通过；重型自动化测试与浏览器动态视觉验收按策略未执行

## 2. 关联需求

- `BASE-ADMIN-002`：管理页面覆盖加载、空数据、失败、无权限和成功反馈。
- `BASE-ADMIN-003`：运营能力与服务端权限一致，只使用生成契约。
- `BASE-ADMIN-006`：提供会员分销财务查询与运营管理能力。
- `BASE-COM-301`、`BASE-COM-302`、`BASE-COM-304`：会员等级、三级推荐与双轨钱包查询事实一致。
- `BASE-LOCAL-001`、`BASE-LOCAL-003`、`BASE-LOCAL-005`：商家/物业附加身份、物业发分与到店核销订单查询。
- `BASE-API-001` 与 `BASE-API-002`：根 `openapi.json` 为唯一 OpenAPI 契约，`packages/api-client/src/` 自动生成。

## 3. 背景

管理端“用户管理”页（`/membership/users`）已具备手机号、商家/物业业务身份与可点击积分列，但在日常运营排查中仍存在四项断点：

1. 业务身份列的“物业”标签尚未与“商家”标签保持对称可点击，且操作列同时存在编辑、管理物业授权、停用/启用、会话、重置密码、删除多个按钮，低频操作占据列表横向空间。
2. 用户列表缺少头像和“会员等级”列，无法按会员等级筛选或直接下钻查看资格贡献与等级升降历史。
3. 用户列表缺少“佣金余额”列与一键查看双轨钱包流水的入口，财务排查需跨页面复制用户标识。
4. 缺少按单用户按需聚合的“用户综合详情抽屉”，查看推荐关系、1/2/3 级团队规模与订单消费概况仍需在多个菜单间往返。

## 4. 目标

1. **P1-A（交互对称与操作列瘦身）**：将“业务身份”列中的物业标签改为可点击直达 `PropertyOperatorEditModal`（具备 `property-operators:read` + `property-operators:update` 且非回收站时），移除右侧操作列“管理物业授权”；将操作列中的“会话”“重置密码”“删除”等低频操作收敛至“更多”下拉菜单。
2. **P1-B（头像、会员等级列与历史抽屉）**：用户首列左侧融合 32px 头像；后端用户列表按 `members:read` 权限批量聚合会员等级并支持按会员等级筛选；管理端新增可点击“会员等级”列与公共 `MemberHistoryDrawer`（双 Tab 查看等级变更历史与资格贡献记录）。
3. **P2（佣金余额列与共享钱包流水抽屉）**：后端用户列表按 `wallets:read` 权限批量聚合双轨钱包摘要，新增 `GET /api/v1/admin/users/{user_id}/wallet-ledgers`（兼容未建账与回收站用户只读审计）；管理端新增公共 `WalletLedgerDrawer`（双轨切换 + 余额概览 + 不可变流水），供用户管理“佣金余额”列与“钱包管理”页复用。
4. **P3（用户综合详情抽屉与跨页跳转闭环）**：后端新增 `GET /api/v1/admin/users/{user_id}/overview`（按各模块权限分段返回基础档案、微信绑定态、活跃时间、会员与三级团队统计、资产速览、订单统计及最近 5 笔订单）；管理端新增 `UserDetailDrawer`，点击用户首列打开，支持一键拉起积分/钱包/会员历史抽屉、点击推荐人站内切换详情，以及带参跳转“订单履约”与“推荐关系”页自动过滤。

## 5. 非目标

1. 不修改数据库表结构，不新增 Alembic 迁移（复用既有索引与外键）。
2. 不向无对应权限的管理员泄露会员等级、积分、钱包或订单数据；不暴露 OpenID/UnionID 明文。
3. 不改变既有推荐绑定、钱包账本、提现审核、积分调整与订单核销业务规则。
4. 不修改小程序端源码、冻结的 Web 端代码或部署配置；不执行未获点名授权的重型测试、构建或浏览器自动化。

## 6. 现状分析

1. `apps/backend/app/services/admin_management.py` 的 `AdminManagementService` 已注入 `actor_permissions`，并在 `list_users` 中按 `points:read` 权限批量查询 `points_accounts`，可直接沿用同一模式按权批量聚合 `member_profiles`、`member_levels` 与 `wallet_accounts`。
2. `member_profiles` 已有 `uq_member_profile_user`、`level_id` 索引及 `ix_member_profile_inviter`；`wallet_accounts` 已有 `uq_wallet_account_user_type`；`orders` 已有 `ix_orders_user_created`。
3. `apps/admin/src/components/AdminAvatar.tsx` 已提供标准头像渲染与首字回退逻辑；`CommerceList.tsx` 当前暂不支持从 URL 注入初始筛选条件，扩展 `initialFilters` 即可平滑承接从用户详情抽屉跳转过来的过滤参数。

## 11. 风险与回滚

- **风险 1（三级团队人数统计在深链或大表下的性能）**：使用按 `inviter_id` 索引的分层集合查询（L1 -> L2 -> L3 最多 3 条索引查询，单用户详情页按需触发，不在用户列表中运行），确保快速响应且避免递归无限遍历。
- **风险 2（越权筛选或泄露敏感字段）**：`member_level_id` 筛选校验 `members:read` 或 `member-levels:read`；综合详情各子模块分别按 `members:read`、`points:read`、`wallets:read`、`orders:read` 裁决返回，绝不返回 OpenID/UnionID 明文。
- **风险 3（URL 带参跳转导致用户无法清空筛选）**：`CommerceList` 仅在挂载时读取 `initialFilters` 同步到表单与查询状态，点击“重置”可正常清空并返回全部数据。
- **回滚方式**：无数据库迁移，直接回退本次提交并重新生成契约即可恢复。
