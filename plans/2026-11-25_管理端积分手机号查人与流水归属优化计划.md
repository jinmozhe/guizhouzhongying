## 3. 背景

管理端积分管理页（`/membership/points`）目前点击“人工授予 / 冲销积分”时要求运营手工输入目标用户 UUID，冲销时还需手抄原流水 UUID；账户列表仅显示 `user_id`，流水抽屉仅截断展示 `source_type: source_id`，既难定位用户，也无法直观区分平台后台操作与物业操作员用户归属。

## 4. 目标

1. 后端新增积分管理专用按手机号查人接口 `POST /api/v1/admin/points-adjustments/lookup-user`（权限 `points:adjust` + CSRF），核验目标用户有效且已绑定手机号并返回用户资料及当前积分余额。
2. 后端新增管理端积分只读编排服务 `AdminPointsService`：
   - 账户列表接口支持按手机号筛选，联查用户表返回用户名、昵称与手机号。
   - 流水列表接口联查管理员表、`property_grants`、`property_operators`、物业操作员用户表以及累计冲销统计，明确展示后台管理员与物业管理员用户 ID/手机号/物业名，并计算每条 `grant` 流水的剩余可冲销积分。
3. `PointsService.adjust` 保留原有全部积分、升级资格与幂等规则（后台发分计入升级资格、物业发分不计入），补充事务内目标用户存在及启用状态校验。
4. 管理端 `PointsPage.tsx` 改造：
   - 弹窗去除手工输入用户 UUID，改为输入手机号自动查询（同时支持手动点击查询），仅在查到有效用户后启用提交按钮，手机号变动立即失效重新核验。
   - 账户列表升级为 `ProTable`，展示用户与去 `+86` 手机号并支持按手机号搜索。
   - 流水抽屉清晰展示中文条目类型、来源渠道与操作人（含物业操作员用户 ID），并对仍有剩余可冲销额度的 `grant` 流水提供“快捷冲销”按钮，自动带入目标用户、原流水 ID 与可冲销上限。

## 5. 非目标

1. 不修改数据库表结构，不新增 Alembic 迁移（沿用 `property_grants.actor_id` 与 `points_ledgers.source_id` 既有设计）。
2. 不改变后台发分计入升级资格、物业发分不计入升级资格的业务规则。
3. 不修改小程序端积分及物业发分接口。
4. 不执行未获授权的 pytest、Vitest、Admin production build、Playwright、浏览器自动化、Git 提交或推送。

## 6. 现状分析

1. `apps/backend/app/domains/points/service.py`：`PointsService.accounts` 与 `ledgers` 仅输出单表 `PointsAccountRead` / `PointsLedgerRead`；`adjust` 未校验目标用户在 `users` 表中的存在与启用状态。
2. `apps/backend/app/api/membership_router.py`：`/admin/points-accounts` 无手机号筛选，`/admin/points-adjustments` 无配套按手机号查人接口。
3. `apps/admin/src/features/membership/PointsPage.tsx`：表单直接要求输入 `user_id` 和 `reverses_ledger_id` UUID，列表未展示手机号，流水抽屉未展示操作人归属与快捷冲销入口。

## 11. 风险与回滚

- 风险 1：自动防抖查人过程中若用户快速修改手机号，旧请求晚返回可能覆盖新状态；前端通过请求序号/当前输入对比丢弃过期响应，并在输入变化时立即清空已确认目标与禁用提交。
- 风险 2：流水抽屉冲销操作复用原 `adjustPoints` 幂等键机制，若中途切换冲销对象需确保 `submitted.current` 在弹窗关闭或切换目标时正确清空。
- 回滚方式：不涉及数据库结构修改，直接回退本任务改动文件并重新生成契约即可恢复。
