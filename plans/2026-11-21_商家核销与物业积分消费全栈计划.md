## 3. 背景

商城需要连接物业、业主和线下商家：平台录入合作商家及物业操作人，物业向已注册并绑定手机号的用户发放积分，用户购买商品时按 SKU 上限使用积分并补足现金，成交后获得核销码，到店由对应商家核销。未核销满七天需要自动退款，核销后的消费形成商家应收，平台通过线下打款完成结算。

这项能力同时改变身份授权、商品报价、订单履约、积分账本、退款恢复和商家财务记录。仅增加“角色字段”“商品商家字段”及核销按钮，无法形成可靠的消费闭环。

## 4. 目标

### 4.1 已确认的功能目标

1. 注册默认拥有会员基础身份；商家、物业作为附加身份，同一用户可以同时具备两种身份，保留普通会员购物能力。
2. 独立商家模块由平台后台维护，以手机号识别核销负责人。一个商家一个手机号，一个手机号管理一个商家，一个商品绑定一个商家。
3. 用户可信绑定手机号后，自动匹配已录入商家并建立身份关联；后台晚于用户注册录入商家也应完成关联。
4. 物业由后台预先指定手机号，或通过手机号搜索已注册用户后人工绑定。物业业务功能限定为给用户增加积分。
5. 积分发放不设置物业总额度、单次业务额度、每日业务额度，不建立小区和房屋归属前置。目标必须是已注册且已验证绑定手机号的有效用户。
6. 积分固定按 `1 积分 = 1 元` 抵扣；每个 SKU 独立配置单件最高可用积分，实际抵扣不能超过用户可用积分、SKU 限额和商品可抵金额。
7. 购买全部完成后才发放核销码；未核销默认七天自动退款，原积分与实际现金分别退回；不提供部分退款。
8. 商家“我的”增加核销入口和核销商品/记录列表，只允许操作本商家的消费。
9. 分类页右侧顶部展示当前分类商家，LOGO 与名称每行四个，多行展示；点击商家只筛选该商家的商品。
10. 商品详情展示商家信息并支持进入商家详情。
11. 本期提供商家应收、对账、线下打款登记与记录查询；实际打款在线下完成。
12. 消费者现金补差统一在小程序订单内调用微信支付，平台依据可信支付事实确认成功后发码，不存在消费者线下付款或商家人工确认收款环节。
13. 当前实际运营只覆盖线上购买、线下到店消费，不开展物流。物业发放积分本身不参与会员升级，积分只用于到店商品。
14. 同商家一单一码，所有明细一次完整核销；不同商家分开下单，不支持部分核销或部分退款。
15. 商家核销应收为订单成交总额，包含积分对应金额，不扣手续费或推荐佣金；积分补贴、推荐佣金由平台另行承担。
16. 含积分订单的返佣计价及消费升级基数均为订单成交总额，包含抵扣积分。总额为既有会员/批发定价后、积分抵扣前的金额，不能使用划线价或参考价。
17. 核销期限从服务端确认成交起算 `7 × 24 小时`；期限内未核销可随时申请整单自动退款，无需商家或后台人工审核。已核销不开放普通退款。
18. SKU 限额覆盖全部成交价且用户积分足够时允许纯积分成交；扣分成功即出码，无需微信零元支付，商家应收、返佣与消费升级继续按完整成交总额计算。

### 4.2 完整业务链

```text
后台创建商家、指定手机号
  → 用户微信识别并可信绑定手机号
  → 自动关联商家身份
  → 后台商品绑定商家、SKU 设置抵扣上限

后台授权物业
  → 物业按完整手机号查询已注册用户
  → 核对用户、输入积分、确认发放
  → 积分账本入账、用户可查询来源

分类选择商家
  → 商品详情查看商家和规格抵扣上限
  → 服务端报价、冻结积分、创建订单
  → 确认现金支付或纯积分成交
  → 扣除冻结积分并签发核销凭证
  → 商家核销
  → 形成商家应收
  → 后台对账、线下打款、登记结清

已成交但七天仍未核销
  → 锁定核销资格
  → 自动发起整单退款
  → 确认现金退回、返还原积分
  → 撤销凭证并完成库存及其他权益补偿
```

消费者付款采用小程序微信支付；现金为零时由服务端确认积分成交。平台向商家打款在线下完成，两条资金动作分别记录，不能混用收款确认和结算登记。

- 复用消费者 Bearer、可信手机号、会员基础账户、商品/SKU、库存预占、订单、真实支付退款、持久任务、资产上传、统一响应、审计和生成契约。

## 7. 方案设计

### 7.1 身份与权限

采用“基础会员 + 商家关联 + 物业授权”的模型，会员等级仍沿用原会员领域。小程序的身份能力返回会员、商家、物业及对应可执行动作；不把权限放进可长期失效的 JWT 快照。

| 主体 | 能力 | 数据范围 |
| --- | --- | --- |
| 普通会员 | 浏览、购买、查询本人积分/订单/凭证、申请允许的整单退款 | 本人及公开资料 |
| 商家身份 | 核销预览、确认核销、查询核销商品和记录、查询本人商家应收及结算记录 | 当前有效关联商家 |
| 物业身份 | 精确查找发放对象、增加积分、查询本人发放结果 | 本次精确匹配用户及本人操作记录 |
| 平台运营 | 商家/物业授权、商品绑定、异常退款处理 | 按独立 Admin 权限 |
| 平台财务 | 商家应收查询、对账、线下打款登记 | 按独立财务权限 |

商家和物业同时存在时，“我的”显示两组入口，不需要切换账户。物业发放记录只服务本项业务的防重和核对，不开放独立用户管理能力。

每次写操作在事务内复查当前账户、会话、角色关联、商家/物业状态和资源归属。停用或解除关联后，新操作立即受权威状态限制；客户端入口刷新仅改善体验。

### 7.2 商家档案与手机号绑定

建议商家字段：

| 字段组 | 字段与规则 |
| --- | --- |
| 标识 | UUID v7 商家 ID、商家名称、状态、编辑版本 |
| 身份关联 | 负责人手机号、绑定用户 ID、绑定时间；有效关联手机号与用户分别唯一 |
| 公开资料 | LOGO 资产、简介、地址、营业时间、公开联系电话 |
| 维护信息 | 创建/更新人、时间、停用原因、人工排序 |

负责人手机号属于授权资料，公开联系电话单独维护，避免因展示联系方式意外开放内部手机号。后台可选择两者一致，但必须明确其公开用途。简介复用受限 HTML 与现有富文本资产治理。

关联流程：

1. 后台新建商家并保存负责人手机号。号码统一规范化后精确匹配有效、已验证手机号的用户；有用户则同事务关联，没有用户则保存待绑定商家。
2. 用户完成可信手机号绑定时，在最外层用例中调用商家公共入口建立关联，事务失败不返回“身份升级成功”。
3. 已注册用户遇到后录入的商家资料无需重新注册；后台保存时关联，登录恢复可幂等校验并补齐合法缺失关系。
4. 后台更换负责人时校验新号码唯一性并保留历史关联事件，撤销旧用户核销权限，新用户权限只在验证关联完成后生效。
5. 商家停用后禁止新购买和新核销，历史应收、核销、订单和退款记录保留；未使用订单仍可进入退款恢复。
6. 商家恢复不会撤销已完成退款，也不会重发已作废凭证。

商家有交易引用后采用停用/归档，不物理删除核心事实。负责人被停用或删除时不能自动把授权转给另一账户；需后台显式修正。

### 7.3 物业授权与发放积分

后台提供两种等价授权入口：

- 录入物业操作名称和指定手机号，等待对应用户完成注册及可信绑定。
- 以完整手机号精确搜索现有已注册用户，核对脱敏资料后绑定物业身份。

首期不建立小区业主关系表、不配置积分资金池或业务额度。任意有效物业可向精确匹配的有效注册用户发放积分；不会因为缺少房号或小区关联拒绝。

小程序流程：

1. 进入“发放积分”，输入完整手机号并查询。
2. 服务端要求当前物业权限，只返回必要的用户昵称、脱敏手机号和可发放状态，不返回用户订单、钱包、他人资产或全站搜索列表。
3. 查询未找到、未绑定手机号、用户停用与服务故障分别处理；不自动替对方注册。
4. 输入正整数积分及业务备注，确认页显示目标和发放数量；再次提交前若手机号改变，原查询结果失效。
5. 提交携带请求 ID、目标用户 ID 和查询关联版本；服务端重查手机号绑定及有效状态，防止查询后目标变化。
6. 同事务完成授权检查、发放业务单、积分余额与流水、审计；成功返回固定业务单和实际到账结果。
7. 网络断开时按原请求 ID 查询；同键同内容返回原结果，同键不同目标/数量明确拒绝。

不设业务额度不等于允许重复记账或无效数值。仍限制为合法正整数，校验存储数值范围，保持账户锁、幂等和接口防滥用。防滥用参数不得被实现为用户未授权的物业日发放额度。

若账户存在原有积分欠款，沿用既有“先偿欠款，再计可用余额”规则，并在确认和结果中明确本次授予、偿欠与可用增加，不能承诺发多少就一定增加多少可用余额。

错误发放由有权限的后台运营根据原流水处理冲销，物业无扣减入口；保留原授予事实、冲销原因和关联流水。

物业授予不创建会员积分资格事件，其冲销也不要求或撤销不存在的积分资格贡献。需要为新来源调整冲销入口，不能直接复用当前“原流水必须有资格贡献”的前置条件。原有其他来源按原政策处理，不追改历史贡献。用户随后花积分购买商品产生的消费升级，按第 7.13 节单独计算。

### 7.4 商品归属、SKU 抵扣与报价

商家归属放在 SPU，SKU 继承所属商家。各 SKU 新增 `max_points_deduction`，表示单件最高可用积分，整数、默认 `0` 表示不支持抵扣。新增履约方式区分到店核销与既有物流/虚拟交付，不能通过是否有商家字段猜测履约方式。

拟采用独立 `fulfillment_mode`，保留既有 `product_type` 的实物/虚拟含义，明确允许组合和数据库约束。到店商品必须绑定有效商家；实物与服务均可按其已配置的到店方式履约，均不进入物流。当前公开售卖、购物车结算及直接下单的服务端入口限定为到店商品，不能仅隐藏物流页面后仍允许创建物流订单。

既有未配置到店方式或未绑定商家的商品暂不进入本期可购集合，后台需显式完成配置后上架；不自动猜测商家或批量改写历史商品、订单。历史订单查询与既有权益处置保留，当前前台不提供地址/物流发货操作作为新购买前置。上线前核对已有在售商品配置清单，避免仅因筛选变更导致商品意外全部不可见。

确定性报价建议：

```text
单件抵扣上限 = min(SKU 配置积分上限, floor(该件按现有规则确定的人民币成交价))
订单可抵上限 = 各订单行数量 × 单件抵扣上限之和
本次实际抵扣 = min(用户选择使用的积分, 用户可用积分, 订单可抵上限)
订单成交总额 = 各订单行按既有会员/批发价规则确定的金额之和
现金应付 = 订单成交总额 - 实际抵扣积分 × 1元
到店订单运费 = 0，不选择收货地址
```

- 单价先按现有会员价/批发价优先级确定，再计算积分；不修改既有价格权利。
- 用户可选择不用积分；启用时建议默认使用本单最多可用积分，提交前明确展示。报价显示所选 SKU、数量、现金原价、单件上限、使用积分和剩余现金。
- 本期积分采用整数。`99.50 元` 的单件商品最多抵 `99 积分`，余下 `0.50 元` 现金支付；不得用浮点或自动四舍五入创造优惠。
- 多行分配必须确定且可重复：按稳定订单行顺序分配用户本次选用积分，各行不超上限；行内单件分配固定，订单保存分配结果。
- 例如售价 `200 元`、SKU 上限 `100`：余额 `160` 时最多用 `100` 积分，补 `100 元`；余额 `80` 时最多用 `80` 积分，补 `120 元`。
- 商品名称、商家、价格、上限、履约政策和结算政策均进入报价指纹及订单快照。报价后改变时要求用户重新确认，不能按新规则静默成交。
- 未绑定商家的历史商品不自动转换为到店商品，不自动赠送积分额度。订单保存下单时商家归属，商品后续改绑不改变旧订单的核销商家和应收主体。
- 当前可购商品全部按到店方式处理，同一商家的实物与服务可以在同一到店订单中购买；若订单的既有 `product_type` 无法表达混合明细，需调整订单级分类约束及投影，保留行级类型，不用“混合类型禁止购买”代替已确认的同商家整单规则。物流/传统虚拟历史订单仍沿用原约束。
- 积分在 API 使用精确十进制字符串，服务端使用整数，前端禁止转为可能失真的 JavaScript Number；金额继续使用 Decimal。

### 7.5 订单、积分冻结与支付

复用现有订单，不新建平行购物订单。新增积分抵扣快照、积分预占、现金支付部分、商家快照、履约方式和结算政策版本。

金额语义必须一次性明确并同步数据库约束、报价、渠道及全部消费者：

- 保留 `items_amount` 表示既有价格规则计算后的商品金额，`freight_amount` 表示运费；订单行保存对应抵扣前金额。
- 新增本单使用积分及 `points_deduction_amount`；固定按 1:1 换算，积分仍作为整数资产单独记账。
- 保留原支付使用的 `total_amount` 为现金应付，约束调整为 `items_amount + freight_amount - points_deduction_amount`；新增明确的 `order_gross_amount` 表达积分抵扣前成交总额，到店运费为零。消费者显示“订单总额、积分抵扣、微信实付”，不能只输出无语义的“总额”让财务或分佣误用现金部分。
- 订单行新增积分分配与现金实付快照，行积分/金额汇总必须等于订单值；商家应收、返佣计价和消费资格使用 `order_gross_amount` 及其行金额，微信支付和现金退款只使用现金实付。
- 付款组成明确区分纯现金、积分加现金、纯积分和原免费订单。纯积分现金为零，仍有积分成本，退款时不能误走“免费订单无需退任何资产”的分支。
- 同步调整现有支付金额校验、支付查询、异常收款退款、账单对账及退款金额约束；现金累计退款上限使用原实际收款，不使用积分前商品价格。

| 阶段 | 积分动作 | 现金与订单动作 |
| --- | --- | --- |
| 报价 | 只读可用余额，不扣分 | 返回权威金额、限额和指纹 |
| 提交订单 | 锁积分账户，将使用量由可用转为冻结；建立订单归属预占 | 同事务预占库存/限购，创建待付款订单 |
| 待支付 | 原冻结保持，其他订单不能重复使用 | 沿用现有付款有效期与支付状态恢复 |
| 成交确认 | 仅消费本订单冻结积分，生成支出流水 | 现金已可信确认或现金应付为零时，成交并发码 |
| 未付款取消/过期 | 原预占仅释放一次 | 明确关单事实后释放库存和限购 |
| 已成交退款 | 按原订单积分返还一次，不按当前 SKU 上限重算 | 现金只退原实际收款；订单保持历史成交事实 |

同一订单重复支付通知、页面重复确认及任务重试不能重复扣积分或发码。积分冻结记录必须保存订单 ID、冻结量、状态及唯一键，账户冻结总额能与有效预占对账。

已确认允许纯积分成交。现金应付为零时仍要确认积分扣减、库存和限购，复用可信内部成交机制并明确积分支付组成，不生成零元微信支付或虚假现金流水。纯积分订单同样进入七天核销、全额商家应收和第 7.13 节权益流程；服务端确认失败时整笔回滚，不发码。

支付结果未知时不能释放积分，也不能发码。先使用原支付参考查询/关单；取消后出现晚到收款时，沿用异常收款退款路径，禁止恢复旧订单并再次扣积分。

消费者现金补差仅使用小程序微信支付；服务端校验可信通知或主动查单结果后确认，客户端支付弹窗成功不作为发码依据。消费者现金退款原路退回原微信支付，不新增线下收款确认或线下消费者退款路径。

### 7.6 核销凭证与商家操作

已确认同一商家的订单一单一码，一次核销全部商品与全部数量，不提供部分核销。购物车可以保存不同商家商品，但结算时明确选择同一商家的一组；跨商家混合提交由服务端拒绝并提示分开购买，不在用户不知情时拆单和自动支付多笔。

凭证包含独立业务 ID、不可预测核销码、订单与商家关联、所有者、有效期、状态和版本。二维码只承载受控核销载荷，不包含姓名、手机号、积分余额、会话 Token 或支付凭据。

核销码需支持用户查看与展示。设计同时覆盖存储和取回：数据库保存检索摘要及受服务端保护的可展示载荷，密钥由受控配置管理；不能只保存不可逆摘要却要求页面再次显示原码。具体生成/保护方案在实现前核验既有依赖，禁止自创加密协议或用订单号直接充当密码。

| 凭证状态 | 可进行动作 | 转移 |
| --- | --- | --- |
| 可核销 | 所属用户展示、对应商家预览和确认 | 已核销或退款锁定 |
| 退款锁定 | 查询退款进展，禁止核销 | 已退款作废；符合规则的拒绝处理后恢复可核销 |
| 已核销 | 查询历史和应收，不能再次核销 | 首期终态 |
| 已退款作废 | 查询历史，不能使用 | 终态 |

七天边界由服务端时间强制检查，任务尚未执行也不能继续核销过期凭证。过期状态可由截止时间派生，持久任务负责发起退款，不以定时任务运行延迟延长权益期限。

商家流程：

1. 从“我的”进入“消费核销”，扫描二维码或手输码。
2. 服务端先校验商家身份和订单归属，再返回商品、规格、数量、应收摘要和截止时间；不能返回其他商家的订单详情。
3. 商家核对后点击确认，提交请求 ID 和凭证版本。预览不占用或核销凭证。
4. 事务内重查身份、订单、退款与凭证状态，原子核销、记录操作者、推进履约、形成应收、记录审计与后续任务。
5. 同一凭证并发核销仅成功一次。相同请求返回原结果，其他重复请求明确显示已经使用。
6. 写结果未知时用原请求 ID 查询，不显示假成功，不自动创建新核销请求。

发码只代表可以消费，实际核销完成才代表到店履约完成。不得调用原管理员虚拟交付接口绕过商家归属、凭证校验、应收和退款保护。

到店订单支付后立即可消费，无需平台或商家另行接单才能核销；原管理员接单、虚拟交付及确认收货接口不得修改到店履约结果。整单核销后产生唯一履约完成事实、开放符合原规则的本人评价，并按既有冻结政策安排佣金结算。扫码者仍须是本商家有效操作人，持有码本身不授予核销身份。

商家列表至少区分“可核销订单”“已核销记录”“退款/作废记录”，展示商品及规格、数量、状态、时间、必要的脱敏消费者信息。可核销列表只提供查看与扫码/输入码入口，不允许仅凭订单 ID 绕过凭证直接核销。

### 7.7 七天自动退款与整单售后

已确认期限从服务端确认成交时起算，精确为 `paid_at + 7 × 24 小时`，界面按北京时间显示截止时间。`now < expires_at` 才可核销，恰好达到截止时间即进入退款处理范围；下单时间、支付按钮返回时间与发码任务延迟不改变期限。

已确认核销和退款都作用于整单。到期前未核销可随时申请整单自动退款，无需商家或后台审核；已核销不开放普通退款。首期不提供核销撤销按钮，操作失误按异常记录与人工处置保留事实，不能删除核销记录或伪造未使用。

退款流程：

1. 用户申请或到期任务锁订单与凭证；核销成功后不能进入普通退款。若退款先取得状态锁，核销拒绝。
2. 到店订单主动退款与到期退款均自动批准，不受原“已接单需人工审核”逻辑阻挡；历史其他履约订单继续按原规则处理。
3. 在同一事务冻结凭证，创建整单退款请求、原现金退款执行意图及积分返还计划。
4. 现金部分原路微信退款；现金为零时只执行内部退款补偿，不伪造渠道退款单。
5. 沿用现有现金确认后补偿的顺序，在现金退款确认成功后，原子完成积分返还、凭证作废、库存回补、佣金撤销/追回及原成交总额的消费资格冲回；纯积分订单直接执行内部补偿。处理中显示现金与积分各自事实，不能提前显示全部到账。
6. 返还积分优先清偿原积分欠款，并分别显示返还总量与可用余额变化；退款不产生新的积分升级资格。
7. 现金未知、渠道失败或补偿失败进入可恢复任务，凭证保持锁定；运维查看失败阶段并按原业务键恢复，不能新建退款重复打款。
8. 重复任务、重复退款通知与人工重试只产生一份退款和一次补偿。

“七天自动取消”在界面表达为“已过期，退款中/已退款”。已成交订单保留 `paid` 事实及独立退款状态，不改回未付款取消，不删除支付或核销历史。

任务采用既有持久任务基础设施，成交同事务登记到期任务，并提供受控补扫恢复。任务执行必须重查最新状态，已核销、已退款或已有退款处理中时幂等结束或跟随原流程。

### 7.8 商家应收、对账与线下结算

应收主体来自订单商家快照，不随商品或负责人改绑转移。核销成功时建立应收，未核销和退款订单不进入待结算应收。

已确认商家应收与实际结算均包含积分对应金额：`商家应收 = order_gross_amount = 消费者现金实付 + 积分抵扣金额`。平台另承担积分补贴及推荐佣金，不从商家款项中扣手续费或佣金；纯积分订单仍全额结算给商家。

例如 `200 元` 成交、`100 积分 + 微信 100 元`，核销后商家应收 `200 元`；若推荐佣金为 `10 元`，商家仍收 `200 元`，平台另承担 `100 元` 积分补贴和 `10 元` 佣金。报表分开展示现金收入、积分补贴、商家应收和推荐佣金，不把积分当成平台已收现金。该示例表达业务金额关系，不新增自动扣款、资金池或财务会计系统。

建议首期台账：

| 记录 | 内容 | 约束 |
| --- | --- | --- |
| 商家应收 | 商家、订单、核销事实、成交总额、积分、现金、平台补贴、应收金额、政策快照 | 每个核销业务仅生成一次，应收不扣佣金/手续费，记录不可覆盖 |
| 对账批次 | 商家、统计区间、明确应收条目集合、金额合计、创建人和状态 | 创建后固定集合，不因筛选变化自动吸入新交易 |
| 对账明细 | 应收 ID、纳入金额、核对状态和争议原因 | 同一有效应收不能重复结算 |
| 线下打款登记 | 批次、实际金额、打款时间、渠道、交易参考、可选凭证资产、登记人 | 人工记录线下事实，不调支付接口，不伪造银行确认 |
| 关联审计 | 创建/核对/撤销草稿/确认付款等事件 | 已付款事实不能删除，错误使用显式冲正 |

后台流程为“筛选未结算应收 → 选择明确条目 → 生成单商家对账单 → 核对 → 线下打款 → 登记打款事实 → 结清”。本期按明确选中条目手工生成批次，不新增自动日结/月结或固定打款周期；每批实际登记金额须与所选应收合计一致。需分批结算时选不同的完整应收条目，不把单条应收拆成多笔部分结清。

商家小程序只读展示应收总额、未结算、已结算和明细，不能编辑财务数值。前端不从当前页推算全量金额，汇总和分页均由服务端完成。

线下结算按独立 Admin 权限操作；登记必须幂等、核对版本、金额与条目，未知结果先查原登记，不能重复登记。完整收款账号等敏感信息不进入公开商家详情、普通核销接口或日志。

### 7.9 分类、详情与“我的”交互

分类页保留搜索、左侧一级分类、二三级筛选和商品连续加载。右侧最上方增加商家区域，随后显示既有范围筛选/结果与商品列表。

- 商家集合由服务端基于当前分类及启用后代中的公开到店商品聚合去重；不另建容易漂移的手工“商家分类”关系，首页推荐、列表、详情和直接下单采用一致运营范围。
- 每行固定四个 LOGO/名称，多个自然换行；单独提供“全部商家”重置入口，不占商家四列格位。
- 点击商家保留当前分类与搜索词，商品查询为“分类范围 + 商家 + 名称关键词”；接口参数参与总数、分页、缓存键与报价商品可见性校验。
- 建议商家候选集合仅依赖分类，关键词只过滤商品，避免选中商家因为关键词变化消失。切换分类清空商家选择，切换商家重置商品分页和滚动。
- 从商品详情返回恢复分类、商家、关键词和浏览位置；旧请求返回不能覆盖新的选择。
- 商家列表采用有界分页并明确“加载更多商家”，每页按四的倍数返回，追加后继续多行展示；不只取当前商品页里的商家，不静默截断为前四家。
- 商家加载失败、没有商家、商品为空、关键词无结果和停用分别表达。没有有效商家到店商品的分类显示真实空态，不回退到未配置商家或物流商品，不伪造平台自营商家。

商品详情商家卡展示 LOGO、名称和必要摘要，点击进入商家详情；未配置商家的旧商品不作为当前到店可售商品，旧链接明确显示不可售，历史订单仍展示原快照。商家详情展示公开介绍、地址、营业时间、公开电话、可售商品及服务状态，不泄露授权手机号。

商品购买区根据所选 SKU 展示实际抵扣上限；积分和现金分开展示，避免把积分抵扣后现金数字当作所有人可得的商品标价。

“我的”沿用当前视觉和公共图标。会员保留现有服务；商家追加核销、核销记录及应收/结算入口；物业追加发放积分入口。身份未绑定、授权撤销、加载和查询失败分别呈现，不能把查询失败降级为普通会员并提示无权限。

跨域写入由明确的 `app/services/` 用例拥有事务，经公开入口调用各领域。只读分类商家聚合、核销列表和财务汇总可使用专门 Query Service，查询结果不能代替写事务中的权威校验。

锁顺序在实现时形成一份全流程矩阵：账户/会话与授权 → 订单 → 退款/凭证 → 积分预占/账户 → 库存与财务条目，并与既有支付/退款锁顺序对齐。现有链路顺序若冲突，须在同一计划调整受影响流程，不能直接新增反向锁。

迁移采用新增 revision：新表、可空商家关联、原履约方式的确定性回填、SKU 积分上限零值、订单快照版本、约束及索引。保留旧订单原金额与履约，不为历史已成交订单补发凭证或生成商家应收。

索引覆盖手机号唯一、商家/状态分页、分类商家可售聚合、待到期凭证、原请求查单和未结算应收。新表保持项目公共列序、UTC、UUID v7、中文字段注释，积分与金额不混用数据类型。

### 7.13 会员升级、返佣与退款联动

已确认“物业授予积分”和“用积分购买后产生消费”采用不同事件：

| 业务动作 | 积分资格贡献 | 消费金额贡献 | 推荐佣金与商家应收 |
| --- | --- | --- | --- |
| 物业授予积分 | 不产生 | 不产生 | 不产生 |
| 物业原发放冲销 | 不冲销不存在的资格事件 | 不直接改变既有消费事实 | 不改写已经成交的订单 |
| 含积分订单可信成交 | 不因积分支出产生积分资格 | 按积分抵扣前成交总额记录一次 | 按完整行成交额适用现有分佣政策，先冻结；商家应收等待核销 |
| 纯积分订单可信成交 | 同上 | 同样按完整成交总额记录 | 不因现金为零跳过分佣，商家应收等待核销 |
| 整单核销 | 不产生 | 不重复累计 | 形成全额商家应收，启动原佣金政策约定的交付后结算等待期 |
| 未核销整单退款完成 | 返还积分不产生新资格 | 冲回该单原完整消费贡献，按原规则重评等级 | 撤销冻结佣金或按原规则追回已结算佣金；无商家应收 |

返佣“按订单总额”落实在行级金额来源：百分比佣金来源按积分抵扣前的行成交额计算，固定每件金额的既有配置保持原语义，继续遵守已发布政策、三级矩阵、总预算 S、总开关、禁用和舍入。不会新增未确认返佣比例，也不会绕过原预算上限把全部成交额发成佣金。

现有 `DistributionService.freeze_commissions_for_payment_in_open_transaction` 的 `base_amount` 参数未直接决定冻结结果，实际读取订单行佣金来源快照。实施须同时核对 `commission_freeze.py` 的来源生成和消费，不能只把入口参数换成总额便宣称适配完成。

沿用现有可信成交时记录消费贡献和冻结佣金、履约后安排结算的时点；到店核销即对应履约完成。原政策快照默认交付后七日结算的含义保持，不能把“购买七天未用退款期限”误作为佣金自动到账时间。

会员升级后影响后续订单的价格；已经确认的本订单保留下单时会员价及等级快照，不因本次升级再计算本单优惠。退款重评会员等级不重写其他既有订单价格或历史推荐关系。永久限购仍按原“成交退款不恢复累计”政策处理，库存按原明细回补；这两项不能混为同一个数量。

### 7.14 本期默认操作边界

以下细节按现有能力与已确认范围落地，不新增关键产品待决项：

- 用户可使用零积分纯现金购买；启用积分时默认计算本单最多可用量，允许选择更少，确认页显示精确金额。不能要求积分不足用户先充值或领取到上限才购买。
- SKU 限额按单件计算并乘购买数量，再受行成交额和余额限制；积分使用整数，小数现金由微信补差。默认限额零，不自动给历史规格开启抵扣。
- 无预约、到店排期或部分消费功能。商家确认核销表示整单全部履约完成，预览必须明确展示所有明细和数量。
- 不新增核销券转赠和账户转移。凭证归订单购买者，本人可展示，系统不额外引入到店实名查验；复制图片不能改变订单归属或退款接收人，只有所属商家有权核销。
- 物业可向任何符合条件的已注册用户发放，包括同时具备商家或物业身份的用户；不额外加入未确认的自发积分禁止规则，均保留操作者与目标审计。
- 商家停用后停止新售卖和新核销，未使用订单继续允许自动退款；不新增“停用即立即批量退款”动作。
- 本期无商家自动结算周期和部分打款模型，运营按完整应收选择批次、线下付款并登记；没有凭证/实际付款事实时不能登记已付款。

## 11. 风险与回滚

| 风险 | 防护与恢复 |
| --- | --- |
| 手机号误绑导致越权 | 可信号码、唯一关联、事务授权、负责人变更审计；撤销后保留历史 |
| 不限额发分的人工误操作 | 明确目标和数量、提交防重、流水追溯及后台冲销；不擅自增加业务额度 |
| 并发抵扣造成超支 | 账户锁、订单归属冻结、唯一请求和守恒校验 |
| 支付成功但未发码 | 同事务业务成交/凭证意图、持久恢复、原单查询；不得再次收款 |
| 核销与退款同时发生 | 同一订单/凭证锁序与条件更新，仅一个流程获得权利 |
| 七天任务停摆 | 请求端时间校验、持久任务、补扫及积压指标；任务失败不延长核销期限 |
| 现金已退但积分未还 | 持久补偿状态、分步骤查询、幂等返还和告警 |
| 平台现金支出高于消费者现金收入 | 按已确认政策记录积分补贴和额外佣金，商家应收不扣费；报表分开显示义务，保留既有返佣预算，不擅自限制物业额度 |
| 商家应收计算错误或重复付款登记 | 不可变快照、一对一业务约束、固定对账集合、事务核验与冲正 |
| 核销码泄露或被穷举 | 最小返回、不可预测载荷、保护存储、失败限流、商家归属检查、日志排除 |
| 商家停用或改绑影响历史消费者 | 历史商家快照，退款持续可用，授权变化不重写消费事实 |

回滚优先停止新发放、新抵扣下单或新核销等独立入口，保留订单查询、退款恢复、补偿与财务核对。不能通过停掉全部任务阻断已发生交易的退款。

新表尚无业务数据时才评估结构降级；已有积分、现金、核销或应收事实后优先前向修复，禁止删表或覆盖余额回到旧状态。数据库恢复、生产回滚与线下付款纠错分别需要准确目标及授权，旧程序若无法识别新订单不得直接替换运行。
