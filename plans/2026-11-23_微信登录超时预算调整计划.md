# 微信登录超时预算调整计划

## 1. 当前状态和结果

- 状态：已结束。
- 结果：已完成；本地超时配套调整、脱敏日志、回归源码和适用轻量门禁完成；真实登录未验收，临时验证目录清理被平台策略拒绝。

## 2. 关联需求

- `BASE-BE-002`：保留统一失败契约，增加不含秘密的请求追踪。
- `BASE-MP-001`、`BASE-QUAL-001`：小程序登录链路调整，区分静态验证和真实平台验收。

## 3. 背景

本地登录多次在约 2 秒后返回 503；不携带登录凭据的独立连接检查复现 `ConnectTimeout`。当前共享 HTTP 客户端连接超时 2 秒，换码总预算 8 秒，小程序请求预算 12 秒。

## 4. 目标

- 仅微信登录换码连接上限调整为 10 秒、换码总预算调整为 15 秒。
- 小程序仅 `/auth/login` 请求使用 20 秒预算。
- 登录换码异常按白名单记录类别、耗时、请求与追踪编号，保留原安全响应。

## 5. 非目标

不改变支付、手机号绑定、共享客户端默认值、微信获取 code 的 8 秒预算、认证开关、密钥、权限或业务响应；不增加自动重试，不执行真实登录、部署或 Git 交付。

## 6. 现状分析

`ConsumerAuthService._exchange` 使用共享客户端，外层 `asyncio.timeout(8)` 限制总时长；小程序传输层所有请求固定 12 秒。异常统一提示未确认，缺少区分连接超时和响应解析失败的日志。

## 7. 方案设计

后端在单次 `get` 指定 `httpx.Timeout(4.0, connect=10.0, pool=1.0)`，外层改为 15 秒。读取和写入仍各 4 秒，连接池等待仍为 1 秒；总预算可能先于分段预算之和到期。前端传输层接受可选 `timeoutMs`，默认 12000，仅登录传入 20000。20 秒覆盖该次后端 HTTP 请求，不包含此前独立获取 code 的时间，也不保证数据库等环节必然在剩余时间内完成。

异常日志仅记录固定依赖、操作和原因枚举、耗时、request_id、trace_id，不记录原异常、URL、code、AppSecret 或微信返回内容。失败仍为原 503，code 确定无效仍为原 401；不重放同一 code。
