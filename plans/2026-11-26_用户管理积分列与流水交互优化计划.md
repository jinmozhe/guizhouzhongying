# 用户管理积分列与流水交互优化计划

## 1. 当前状态和结果

- 当前状态：已结束
- 结束结果：已完成；后端用户列表按权批量聚合积分余额、新增按用户查询积分余额与流水接口、OpenAPI 与 API Client 同步、管理端抽离公共积分流水抽屉并完成用户管理与积分管理页改造均已交付，全栈轻量与仓库治理门禁全部通过；重型自动化测试与浏览器动态视觉验收按策略未执行

## 2. 关联需求

- `BASE-ADMIN-002`：管理页面覆盖加载、空数据、失败、无权限和成功反馈。
- `BASE-ADMIN-003`：运营能力与服务端权限一致，只使用生成契约。
- `BASE-ADMIN-006`：提供会员分销财务查询与运营管理能力。
- `BASE-LOCAL-003`：物业发分可追溯，发放错误由受权后台按原流水纠正冲销。
- `BASE-API-001` 与 `BASE-API-002`：根 `openapi.json` 为唯一 OpenAPI 契约，`packages/api-client/src/` 自动生成。

## 3. 背景

管理端“用户管理”页面（`/membership/users`）目前存在两处体验与信息架构问题：

1. 列表未展示用户当前积分余额，也无法从用户列表直接查看该用户的积分流水明细；运营要查某人积分及来源时，必须切到“积分管理”（`/membership/points`）再重新搜索手机号。
2. 用户管理列表右侧操作列已包含编辑、管理商家授权、管理物业授权、调整积分、启停、会话、重置密码、删除等最多 8 个按钮，横向拥挤；同时直接点击行尾“调整积分”时无法先查看历史发放与消费流水，既容易重复发分，也无法直接选中某笔授予流水执行快捷冲销。

## 4. 目标

1. 在管理端用户管理页面（`/membership/users`）新增“积分”列，展示用户积分余额；无论积分为 0（含历史未初始化积分账户用户）还是非 0，点击该单元格均可打开该用户的积分流水面板。
2. 明确积分流水的展示载体与交互层次：采用**宽版右侧抽屉（Drawer）**呈现用户积分余额概览与不可变流水明细，并抽离为公共组件与“积分管理”（`/membership/points`）复用，保持全站交互统一。
3. 收敛“调整积分”入口：将用户管理列表右侧操作列的“调整积分”按钮移入点击积分后打开的积分流水抽屉头部，同时在流水表格中保留对可冲销授予流水的行内“冲销”按钮，形成“先看账、再动账”的运营闭环。
4. 保持服务端权限与数据事实严格一致：仅在管理员具备 `points:read` 权限时由服务端返回积分余额摘要与流水，不把无权限或读取失败伪装为 0；按 `user_id` 查询流水时，未建账用户稳定返回空流水列表，不报 404，也不在只读查询中产生建账写副作用。

## 5. 非目标

1. 不修改数据库表结构，不新增 Alembic 迁移（复用既有 `points_accounts` 与 `points_ledgers` 及 `uq_points_account_user` 唯一索引）。
2. 不改变现有积分授予计入升级资格、物业发分不计入升级资格、冲销回退及幂等校验规则。
3. 不移除独立菜单“积分管理”（`/membership/points`）及其全局手机号搜索、手动查人发分能力。
4. 不修改小程序端源码、冻结的 Web 端代码或部署配置。
5. 本次阶段仅完成方案规划与计划文档登记；在用户确认方案与授权实施前，不修改业务源码，也不执行未获授权的测试、构建、浏览器自动化或 Git 远端操作。

## 6. 现状分析

1. **后端用户列表与积分模型**：
   - `GET /api/v1/admin/users` 在 `apps/backend/app/services/admin_management.py` 中通过 `AdminManagementService.list_users` 组装 `AdminUserRead`，当前仅批量关联了 `merchants` 与 `property_operators`，未关联 `points_accounts`。
   - `points_accounts` 表已具备 `uq_points_account_user`（`user_id` 唯一索引），批量 `IN (user_ids)` 查询可走索引且无 N+1 风险。
   - 历史用户可能尚未初始化 `points_accounts` 记录，而现有流水接口 `GET /api/v1/admin/points-accounts/{account_id}/ledgers` 强依赖 `account_id`，无法直接支撑从用户列表点击 0 积分或未建账用户查看流水。
   - `apps/backend/app/api/dependencies.py` 的 `get_admin_management_service` 已持有 `current: CurrentAdmin`（包含 `current.permissions`），可直接用于服务端按 `points:read` 权限控制余额聚合。
2. **管理端现状**：
   - `apps/admin/src/features/users/UsersPage.tsx` 操作列已有“调整积分”按钮，直接拉起公共组件 `apps/admin/src/components/PointsAdjustModal.tsx`；由于列表无余额与流水入口，调整前无法核对历史流水，且操作列过于拥挤。
   - `apps/admin/src/features/membership/PointsPage.tsx` 已实现 9 列不可变积分流水抽屉（`Drawer size={960}`），包含中文条目类型、可用/冻结/欠额变动、平台管理员与物业操作员归属（含物业 UID）、剩余可冲销额度及行内“冲销”按钮。
   - 全管理端查看子流水的既有范式统一为右侧 `Drawer`（如 `UsersPage` 会话抽屉 `560px`、`MembersPage` 资格/等级抽屉 `720px`、`PointsPage` 积分流水抽屉 `960px`、`WalletsPage` 钱包流水抽屉 `1000px`）。

## 7. 方案设计

### 7.1 交互形态选型评估（抽屉 vs 弹窗 vs 独立路由）

| 维度 | 方案 A：宽版右侧抽屉 Drawer（推荐） | 方案 B：居中大弹窗 Modal | 方案 C：独立子路由页面 |
| --- | --- | --- | --- |
| 上下文保持 | 保留用户列表当前筛选、关键词、分页与滚动位置，关抽屉原地回到原行 | 保留列表上下文 | 跳转后往返易丢失筛选与位置，批量核查效率低 |
| 宽表承载力 | `size={960}` 占满视口高度，容纳 9 列流水表、分页及顶部资产摘要无压力 | 高度受限，20 行表格易出现双层滚动条与挤压 | 承载力强，但与已有 `/membership/points` 菜单定位重叠 |
| 二次操作层次 | Drawer 内点“调整积分 / 冲销”弹出居中 `PointsAdjustModal`，层次自然清晰 | 形成 Modal 叠 Modal，遮罩压暗、焦点与 Esc 冲突风险高 | 弹窗不叠加，但往返成本高 |
| 全站一致性 | 与积分管理、钱包流水、会员资格流水、用户会话完全一致，可直接抽离复用 | 破坏现有流水抽屉统一风格 | 引入额外隐藏路由与面包屑维护成本 |

**规划结论**：采用 **方案 A（宽版右侧抽屉 `Drawer`，`size={960}`）**，并抽离公共组件 `apps/admin/src/components/PointsLedgerDrawer.tsx`，供 `UsersPage.tsx` 与 `PointsPage.tsx` 共同复用。

### 7.2 “调整积分”入口迁移评估

- **规划结论**：建议将用户管理列表右侧操作列的“调整积分”按钮**移入积分流水抽屉头部（右上角 `extra` 操作区）**，并同步在抽屉流水表格行内开放可冲销流水的“冲销”快捷按钮。
- **核心收益**：
  1. **先看账再动账**：点击积分后先看到当前实时余额（可用 / 冻结 / 欠积分）与历史发放/消费/冲销流水，再决定新授予或对某笔误发流水执行精准冲销，大幅降低重复发分和误冲销风险。
  2. **彻底告别手抄流水 UUID**：原来从用户管理点“调整积分”切到冲销模式时，运营仍需手动输入原流水 UUID；移入流水抽屉后可直接点击对应授予流水的“冲销”按钮自动带入原流水与可冲销上限。
  3. **操作列大幅减负**：用户管理右侧操作列减少 1 个高频宽按钮，聚焦账户资料、业务授权与安全状态管理；所有积分读/写动作收敛于“积分”列单一入口。
- **细粒度权限兜底**：
  1. 同时具备 `points:read` + `points:adjust`：列表显示真实积分，点击打开抽屉看余额与流水，支持右上角“调整积分”及行内“冲销”（停用或回收站用户禁用写操作并提示）。
  2. 仅有 `points:read`：列表显示真实积分，点击打开抽屉纯只读查看余额与流水，隐藏全部写按钮。
  3. 仅有 `points:adjust`（无 `points:read`）：服务端不返回余额；列表“积分”列不伪造 0，展示“积分操作”可点击入口，点开抽屉后流水区明确提示缺少 `points:read` 查看权限，但右上角仍保留“调整积分”按钮，不阻断既有授权能力。
  4. 既无 `points:read` 也无 `points:adjust`：列表不展示“积分”列。

### 7.4 Backend 技术设计

1. **扩展用户列表响应模型（`apps/backend/app/domains/admin/schemas.py`）**：
   - 新增 `UserPointsSummary(BaseModel)`：`account_id: uuid.UUID`、`available_points: int`、`frozen_points: int`、`debt_points: int`。
   - 在 `AdminUserRead` 增加可选字段 `points_summary: UserPointsSummary | None = Field(default=None, description="用户积分账户摘要；无 points:read 权限或尚未初始化积分账户时为空")`。
2. **按权限批量聚合积分余额（`apps/backend/app/api/dependencies.py`、`apps/backend/app/services/admin_management.py`）**：
   - 在 `AdminManagementService` 注入 `actor_permissions: frozenset[str]`。
   - 在 `list_users` 与 `restore_user` 中，仅当 `PermissionCode.POINTS_READ.value in self.actor_permissions` 时，按当前页 `user_ids` 执行单条 `SELECT ... FROM points_accounts WHERE user_id IN (...)` 批量映射 `points_summary`；无 `points:read` 权限时不查询且保持 `None`。
3. **新增按 `user_id` 查询积分账户与流水的聚合端点（`apps/backend/app/services/points_admin.py`、`apps/backend/app/api/membership_router.py`）**：
   - 新增 `AdminUserPointsLedgersRead(BaseModel)`，包含 `account: PointsAccountRead | None` 与 `ledgers: PageResult[AdminPointsLedgerRead]`。
   - 新增路由 `GET /api/v1/admin/users/{user_id}/points-ledgers`，声明 `PermissionCode.POINTS_READ`。
   - 编排逻辑：
     - 先查 `User` 是否存在（含已软删除用户，允许审计历史流水；仅用户完全不存在时抛出 404 `USER_NOT_FOUND`）。
     - 按 `PointsAccount.user_id == user_id` 查询积分账户：
       - 若存在，返回 `account` 并复用抽离的 `_ledgers_for_account(account.id, page, page_size)` 返回完整归属信息与可冲销额度。
       - 若尚未初始化积分账户，返回 `account=None` 与空分页 `PageResult(items=[], total=0, page=page, page_size=page_size)`，不报 404，也不产生写副作用。

1. **API 封装（`apps/admin/src/lib/api/commerce.ts`）**：
   - 新增 `userPointsLedgers(userId: string, page?: number, pageSize?: number)`，消费生成的 `AdminUserPointsLedgersRead` 类型。
2. **新增公共组件 `apps/admin/src/components/PointsLedgerDrawer.tsx`**：

   - 抽屉结构：
     - 标题：`积分不可变流水 - {昵称或用户名}（{去 +86 手机号或未绑定}）`。
     - 右上角 `extra`：具备 `points:adjust` 时展示“调整积分”主按钮；若用户已停用或已软删除则禁用并以 Tooltip 说明原因。
     - 顶部余额摘要条：具备 `points:read` 且加载成功时展示实时可用积分、冻结积分、欠积分；未初始化账户时提示“当前用户尚未初始化积分账户（余额 0），首次人工授予或业务发分时自动建账”。
     - 主体流水表：9 列完整流水表（与当前 `PointsPage.tsx` 保持一致），固定 `scroll={{ x: "max-content" }}` 与 `white-space: nowrap`；仅在具备 `points:adjust` 且目标用户处于启用未删除状态时，对仍有剩余可冲销额度的 `grant` 流水显示“冲销”按钮。

3. **改造用户管理页（`apps/admin/src/features/users/UsersPage.tsx`）**：
   - 在“业务身份”列之后新增“积分”列（仅当管理员具备 `points:read` 或 `points:adjust` 时渲染该列）：
     - 具备 `points:read` 时，无论余额为 `0` 还是正数（含未建账用户显示 `0`）均渲染为可点击链接按钮；若存在 `frozen_points > 0` 或 `debt_points > 0`，在数字旁提供紧凑角标/副标并在 Tooltip 展示完整三项明细与未建账说明。
     - 仅有 `points:adjust` 时，展示可点击的“积分操作”入口。
     - 回收站（`lifecycle === "deleted"`）视图同样保留积分列，可点击查看历史只读流水，写按钮自动禁用。
   - 移除右侧操作列中的“调整积分”按钮与顶层直挂的 `PointsAdjustModal`，改为点击“积分”列打开 `PointsLedgerDrawer`。
4. **同步积分管理页（`apps/admin/src/features/membership/PointsPage.tsx`）**：
   - 复用 `PointsLedgerDrawer` 替代原有内联流水抽屉，保留顶部“人工授予 / 冲销积分”与表格内“积分流水”“人工调整”原有功能，消除双份流水表格维护。

## 11. 风险与回滚

- **风险 1（未建账历史用户点击 0 积分报错）**：历史用户可能不存在 `points_accounts` 记录。缓解：后端新增按 `user_id` 查询接口，用户存在但未建账时返回 `account=None` 与空分页列表，前端清晰提示并在首次授予成功建账后立即刷新出余额与首条流水。
- **风险 2（越权暴露用户积分余额）**：`GET /api/v1/admin/users` 原本仅校验 `users:read`。缓解：服务端仅在管理员具备 `points:read` 时批量查询并填充 `points_summary`；无查看权但有 `points:adjust` 权限的管理员仍可通过抽屉右上角完成调整，不阻断业务也不泄露余额。
- **风险 3（两处抽屉缓存未联动导致数字陈旧）**：在用户管理抽屉内完成授予或冲销后，若未刷新列表缓存会出现抽屉与背景行余额不一致。缓解：调整成功后统一失效 `["admin-users"]`、`["admin-user-points-ledgers", userId]`、`["admin-points-accounts"]` 与 `["admin-points-ledgers"]`。
- **回滚方式**：不涉及数据库表结构与迁移变更，直接回退本次代码改动并重新生成 OpenAPI 契约即可完整恢复。
