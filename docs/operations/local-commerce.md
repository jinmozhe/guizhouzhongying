# 到店核销、物业积分与商家结算

## 1. 适用范围与前置

本手册对应迁移 `20261121_01` 及到店业务源码。当前新购仅支持同一商家整单到店消费；历史物流与虚拟履约数据和代码保留。代码与轻量检查不代表数据库已经升级、微信支付已经开通或真机验收已经通过。

业务政策见[产品需求基线](../PROJECT_REQUIREMENTS.md)，实施和未执行项见[全栈计划](../../plans/2026-11-21_商家核销与物业积分消费全栈计划.md)。消费者现金只走小程序订单内微信支付，商家结算采用平台线下付款后的人工登记。

启用前依次完成：

1. 核对目标环境、备份与授权后，将数据库从已有版本升级至 `20261121_01`。旧库会被现有 Readiness 版本检查拒绝。各环境执行结果以全栈计划记录为准，不能将本机迁移结果视为测试库或生产库结果。
2. 按[认证授权边界](../architecture/authentication-authorization.md)和 `scripts.sync_permissions` 的检查、应用流程同步六项权限：`merchants:read`、`merchants:update`、`property-operators:read`、`property-operators:update`、`merchant-settlements:read`、`merchant-settlements:update`。商品维护人员同时需要商家查看权限。
3. 在 API 和 Worker 的受控环境中配置相同的 `LOCAL_REDEMPTION_KEY`，使用独立 Fernet 密钥并安全备份。模板留空；缺失时新到店订单明确拒绝，已存在凭证无法解密时也会明确报错。无默认密钥，不把密钥输出到日志或提交仓库。
4. 沿用[微信支付手册](wechat-pay.md)配置支付、退款恢复和发货管理。到店核销后的现金订单上报自提履约，纯积分订单不调用微信支付和发货接口。
5. 按既有 Worker 托管方案运行 `scripts.run_durable_tasks`，启用任务失败告警。七天退款依赖 Worker 持续处理，API 请求进程不承担定时调度。
6. 独立授权后完成真实 PostgreSQL 并发与回滚、微信付款退款、自提上报、二维码显示扫码及两端人工验收，再开展实际交易。

现有未核销凭证由当前密钥保护，不允许直接丢弃或替换密钥。轮换必须先制定对存量凭证重新加密及恢复的专项方案；本期未提供无期限多密钥自动尝试。

## 2. 建档、角色与商品

后台左侧“工作台”下方的“商家&物业”菜单提供商家、物业授权、应收与结算页面。新增或编辑商家和物业授权时直接输入 11 位中国大陆手机号，表单和列表只显示手机号。保存或在授权表单查询已注册用户时自动补上 `+86`，后端以 E.164 格式匹配用户并在保存时写入对应的数据表。先建档再注册、先注册再建档均可关联，微信可信绑手机和历史用户登录会补关联。后台更新授权手机号会解除旧关联并重新匹配，保留历史事件。

会员身份、附加业务身份、会员等级与管理员 RBAC 相互独立。管理端“用户管理”页聚合展示用户的商家和物业业务身份（含名称与启用/停用状态）并支持按业务身份筛选；仅当用户已关联商家或物业且当前管理员拥有对应查看与更新权限时，提供“管理商家授权”或“管理物业授权”入口直接拉起既有编辑弹窗（沿用原接口、权限与乐观锁 `revision`），无关联身份时不显示按钮，也不在用户管理页提供新建商家或物业授权入口。小程序“我的”页面消费 `/users/me/business-roles` 返回的身份摘要，在顶部个人信息区展示当前会员与关联商家/物业名称及启停状态；停用授权后实时失去核销或发分入口及业务操作能力，商家停用后停止新售卖及核销，历史订单退款继续处理。商家详情仅公开名称、LOGO、受限 HTML 介绍、地址、营业时间、公开电话和启用状态，不公开授权手机号。

新建商品固定为实物，选定唯一商家并按到店核销履约。各 SKU 分别维护单件积分上限，新建规格、逐条编辑和批量派生均可填写。旧商品可保留历史履约资料，关联商家后显式转为到店模式。历史订单使用成交商家快照，不随商品改绑转移。

管理端新建商品时，默认 SKU 和每个销售规格组合均预填初始库存 10000 件。保存前可按实际需要调整。

## 3. 物业发放与积分计算

物业在“我的”进入发分页面，输入完整手机号查询已注册且可信绑定的会员，核对姓名、脱敏手机号及积分后提交。不限制小区、业务总额度、单次或每日业务额度。接口每账户每分钟 120 次的技术防滥用控制不改变业务额度，超限返回 429，Redis 不可用时明确失败。

发分使用独立请求号和目标手机号验证时间快照。结果未知时保存原内容，可查原结果或使用原请求恢复，禁止换请求号重复发放。发放记录仅返回本人实际发出的记录。金额以整数积分字符串传输，避免前端大整数精度丢失；数据库 BIGINT 的可表示范围属于存储约束。

物业来源积分先抵扣已有积分欠款，再增加可用余额，不写入会员积分资格事件。后台沿用原授予流水冲销能力，物业来源冲销同样不撤销不存在的资格事件。

报价先计算会员价和批发价，再逐件计算可抵积分。单行上限为 `min(SKU 配置上限, 向下取整后的成交单价) × 数量`，全单上限同时受可用余额约束。按 SKU 标识排序分配行积分，保证重试与退款快照稳定。1 积分抵 1 元，金额使用 Decimal，现金保留两位小数。

| 示例 | 成交额 | 积分 | 微信应付 | 核销后商家应收 |
| --- | --- | --- | --- | --- |
| SKU 上限 100，用户有 160 积分 | 200.00 | 100 | 100.00 | 200.00 |
| SKU 上限 100，用户有 80 积分 | 200.00 | 80 | 120.00 | 200.00 |
| SKU 售价及上限均为 100 | 100.00 | 100 | 0.00 | 100.00 |
| 单价 10.50，购买两件，上限覆盖售价 | 21.00 | 20 | 1.00 | 21.00 |

下单冻结积分及库存，成交将冻结积分转为支出；未成交取消释放积分。返还时仍按原积分账户规则抵扣已有欠款，不产生新的升级资格。

## 4. 成交、核销与退款

现金付款成功由原可信微信链路确认。纯积分订单在服务端扣分成功后内部成交，不创建零元微信支付。两者都生成一张随机码凭证，凭证明文只供买家本人查看；存储 SHA-256 查询摘要及 Fernet 密文，二维码由服务端生成。

凭证截止时间从服务端接受成交并建凭证的时刻起计算 7×24 小时。商家扫码或输入码后先预览商品及完整金额，确认全部消费后整单核销。服务端重新核验用户、会话、当前商家关联、订单归属、截止时间、退款及履约状态；核销与退款共用订单锁，重复原请求返回已有事实。

未核销可主动整单自动退款，无人工审核；到期任务 `expire_redemption` 使用稳定业务键和原退款请求号执行同样的整单逻辑。任务与凭证同事务建立，无需依赖客户端触发。超过失败阈值后进入 attention，后台核对原因并按既有版本化任务恢复流程恢复。

现金退款确认前，凭证为退款中，积分仍未返还。现金资金确认后同事务完成积分返还、库存回补、原消费贡献冲回、原佣金撤销或追回和凭证作废。纯积分直接执行内部补偿。订单仍保留 paid 及原成交事实，退款状态独立展示。已核销不开放普通退款。

## 5. 应收、对账与纠错

核销成功同事务建立唯一订单应收，金额满足：

```text
商家应收 = 原成交总额 = 微信实付 + 积分抵扣金额
平台另承担积分补贴及推荐佣金
```

返佣按原完整商品行金额及既有分佣政策计算，核销启动原政策的交付后佣金结算等待期。商家应收不扣手续费或佣金。未核销及退款订单不进入应收。

后台选中同商家 1 至 100 条尚未组批应收，一次事务创建完整对账批次。组批后条目固定，不存在可编辑的中间草稿；批次可以选择导出，商家可以查看本人应收与批次。查询结果使用当前接口读取快照，不替代线下银行或微信凭据。

线下付款后填写全额、真实付款时间和凭据号登记。重复请求不重复记账，相同凭据不能用于其他当前已付款批次，金额或版本变化明确拒绝。结果未知先刷新原批次及付款历史，使用原提交内容恢复。

错误登记使用“纠错冲正”：填写原因、核对原批次后恢复待付款状态，并追加独立冲正事件。原付款与冲正历史永久保留，不删除付款事实；该操作不执行真实退款或转账，后续付款登记必须再次核对实际线下资金。

## 6. 数据与锁序

新表、字段与实际迁移差异见[数据库字典](../architecture/database-schema-guide.md#135-到店商家物业积分核销及结算)。商家、物业、核销和结算由独立应用服务与 Repository 管理，积分状态转换由积分域拥有，交易服务持有跨域事务。

| 用例 | 按先后取得的主要锁 |
| --- | --- |
| 微信登录、可信绑手机、后台业务身份维护 | 业务关联保护锁，用户，业务身份；各入口既有身份/会话锁同时保留 |
| 物业发分 | 业务关联保护锁，排序后的操作者/目标用户，操作者会话及物业授权，积分账户 |
| 下单及纯积分成交 | 推荐关系保护锁，业务关联保护锁，用户与下单幂等，目录，积分，库存/限购，会员与分佣 |
| 渠道付款后确认订单 | 推荐关系保护锁，业务关联保护锁，用户，订单/付款，目录，积分，库存/限购，会员与分佣 |
| 取消或退款补偿 | 订单及原请求/凭证，目录，积分，库存/限购，再原佣金和会员贡献 |
| 商家核销 | 业务关联保护锁，当前用户/会话/商家，订单，凭证/退款/履约，再应收与佣金任务 |
| 对账和付款登记 | 后台身份/权限/审计，业务关联保护锁，批次或排序后的应收条目 |

用户行采用 NO KEY UPDATE，保留外键 KEY SHARE 能力。业务关联保护锁当前粒度较粗，后续优化须有并发证据并保持绑定、发分、核销的最终授权边界。

## 7. 验证与运行限制

新增真实 PostgreSQL 回归源码覆盖物业幂等发分、授予无升级资格、SKU 上限、混合支付报价、纯积分成交、原单恢复、核销归属、全额应收、主动及到期退款和积分余额。测试源码不等于已执行证据。

本机开发库已在追加授权后完成迁移、权限目录同步和结构/数据核验，证据见[全栈计划](../../plans/2026-11-21_商家核销与物业积分消费全栈计划.md#153-本机开发库迁移与权限同步)。pytest、Vitest、构建、真实微信资金或真机验收未执行。官方资料搜索与读取未取得有效结果，当前微信自提上报参数、扫码和二维码渲染仍须在正式接入时结合官方接口及真机验收核实；不把静态类型检查写成平台可用性证明。
